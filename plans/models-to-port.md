# Models to port

> Paths in this file — `dev/Lava`, `dev/JuliaVision`, `tools/`, `gen/` — are relative to the
> **workspace root**: the untracked scratch directory that contains `dev/`. This file used to
> live there; it moved into the repo so all three machines share one copy.


Nine models, one editor feature each, chosen so that none of them overlaps
another. Everything here has been checked for two things that are easy to get
wrong late: whether the licence permits the use, and whether the weights sit at a
stable direct URL that Julia's artifact system can fetch without a human clicking
a consent form.

The editor stays MIT. Each model is its own package, so a package may carry a
different licence — `ProPainterRunner` is non-commercial, exactly as
`MatAnyoneRunner` already is. What the editor must not do is *depend* on one of
those; it has to degrade without them.

Companion files: `tools/models.py` is the machine-readable registry (URLs,
licences, package names) that the fetcher and the scaffolder both read, and
`kernelbot.md` is the kernel corpus to mine while writing the missing ops.

## Status

`state` is one of: **scaffolded** (package exists, loads, no export yet) ·
**exported** (graph JSON + weights on disk) · **runs** (executes on Lava,
output unverified) · **verified** (matches PyTorch) · **shipped** (in the editor
with a workload and no cold start).

Two target columns on purpose. **vs PyTorch** is the engine goal and the one
`perf-plan.md` argues about — SAM 2 sits at 64% on decode and the gap is
diagnosed. **The editor budget** is what makes the feature usable at all, and it
is the one that decides whether a port was worth doing: a depth model at 3x
PyTorch that still takes 400 ms a frame does not buy a depth-keyed grade.

## What is already set up

Done, and verifiable:

- **Weights fetched** — 2.4 GB across eight models, in `gen/<name>/`.
  `uv run tools/models.py list` shows what is present;
  `uv run tools/models.py fetch --all` is idempotent. Only the neural LUT is
  outstanding, and its weights live in the upstream checkout rather than at a URL.
- **Nine packages scaffolded** in `dev/JuliaVision`, generated by
  `tools/newrunner.py` from the registry. Each has `Project.toml`,
  `src/<Package>.jl` and `test/runtests.jl`, and each loads with no assets
  installed — verified by loading all nine.
- **Wired into the monorepo environment** (`dev/JuliaVision/Project.toml`).
  Deliberately *not* into the editor's own `Project.toml`: an unported model has
  no business in the environment that has to start reliably.
- **Licences and gating checked** against the GitHub and HuggingFace APIs rather
  than assumed. Findings are in the per-model sections below; two of them changed
  the pick.
- **One export working end to end** — `tools/export_whisper.py` produces
  `gen/graphs/whisper`, and `WhisperRunner` loads its 617 ops from Julia. It is
  the template the other eight follow: load the module, name the inputs, export
  from CUDA, hand the `ExportedProgram` to `export_graphs.convert`.

Not done: eight of the nine exports, the missing ops, and every workload body.
Those are the port.

## Order, and why

1. **FFT/STFT + Whisper.** Biggest editor feature by a distance — transcript-driven
   editing is what Premiere and DaVinci sell on. One FFT kernel then unlocks
   DeepFilterNet, Demucs and Kokoro, so it is four models' worth of groundwork.
   It also forces a KV cache, which puts the engine in a bandwidth-bound batch-1
   GEMV regime that none of the GEMM tiling work applies to.
2. **Neural 3D LUT.** Days, not weeks, and immediately visible. Nothing new for
   the runtime.
3. **RIFE.** Cheap — the warp is `grid_sampler_2d`, already implemented. Blocked
   only on mirroring the weights.
4. **DeepFilterNet3.** Nearly free once the FFT exists.
5. **Depth Anything V2 Small.** No new ops at all, pure editor value.
6. **BasicVSR++.** Already exported; the deformable conv is the hardest kernel here.
7. **Demucs.** Wants a device-side FFT rather than a host-side one.
8. **Kokoro.** The LSTM fight. Take it when the rest is landing.
9. **ProPainter.** Compounds SAM 2, which is the argument for it.

## Whisper large-v3-turbo — speech → text

- **Package** `WhisperRunner` · **Licence** MIT · **Weights** `gen/whisper` (1.6 GB, fetched)
- **Upstream** https://github.com/openai/whisper · loadable from `transformers`
- **Export** `tools/export_whisper.py` — **works**, encoder only

809M parameters. MIT and ungated, so this one could live in the editor package
itself rather than beside it.

**The encoder is exported and needs no new ops.** 617 nodes over 11 distinct
ATen ops, all 11 already implemented — checked against the runtime's op set
rather than assumed. `WhisperRunner.ready()` is true and `whispergraph()` loads
it. That makes the encoder a straight bring-up rather than a kernel project, and
it means the FFT and the KV cache — the two things Whisper is here to force —
are the *decoder's* problem, not a prerequisite for first light.

Two findings from doing it:

- **Export from CUDA or the attention decomposes.** `export_sam2.device` already
  documents this and it cost the same here: a CPU export gave 969 nodes with 64
  `bmm`, an explicit `_softmax`, and the `logical_not`/`where`/`any.dim` cluster
  that guards fully-masked rows. From CUDA it is 617 nodes with 32
  `_scaled_dot_product_efficient_attention` and no `bmm` at all. For 32 blocks of
  (1, 20, 1500, 1500) attention the difference is ~180 MB of materialised matrix
  per block. The exporter now refuses a silent CPU export.
- **fp32 encoder weights are 2.55 GB**, against the 1.6 GB fp16 checkpoint they
  came from. Worth an fp16 export before anything is benchmarked — the encoder is
  635M of the 809M parameters and this is the number that decides whether it sits
  alongside SAM 2 comfortably.

Next on this one: run the graph on Lava and diff against PyTorch, then the mel
front end, then the decoder.

**Why this and not Parakeet — corrected 2026-08-02.** NVIDIA's Parakeet TDT 0.6B
is faster and scores higher on English leaderboards, and on the feature itself it
would probably be the better pick. **It is English-only, and that decides it**:
Whisper large-v3-turbo transcribes ~99 languages, and a transcript tool that
works for one of them is a different, smaller product.

The two reasons this paragraph used to give were both weak and are recorded here
so they do not get re-used:

- *"CC-BY-4.0 drags attribution downstream"* — inconsistent with our own list.
  `ProPainter` is already here as **non-commercial**, which is far heavier than
  attribution. If that is acceptable, CC-BY is.
- *"Whisper forces a KV cache, and that execution mode transfers to every LLM or
  VLM after it"* — true, and not a reason to pick a **product** feature. Nothing
  else on this list needs a KV cache: DeepFilterNet, Demucs, Kokoro, NeuralLUT,
  RIFE, Depth Anything, BasicVSR++ and ProPainter have no autoregressive decode,
  and FLUX / Z-Image / Qwen-Image-Edit are diffusion, where a DiT has no causal
  cache. It was engine-roadmap reasoning applied to a feature decision, which is
  backwards from this file's own rule that the *editor budget* decides whether a
  port was worth doing.

The KV cache remains a genuine **side benefit** — it is the first batch-1,
bandwidth-bound GEMV workload the engine will have run, and none of the GEMM
tiling work applies to it — but it is not why Whisper won.

**Parakeet is worth keeping on the shelf**, deprioritised rather than rejected: if
an English-only fast path is ever wanted it is a strong candidate, and the mel
front end is shared so the FFT work is not wasted either way. Two things would
need checking first and neither is known: whether a **NeMo** model gives up an
`ExportedProgram` as cleanly as a `transformers` one, and whether its TDT
prediction network is an **LSTM** — which would put it behind the same fight
Kokoro is deferred for.

**New ground:** an FFT for the log-mel front end (host-side is acceptable to
start — it is tiny next to the encoder), and incremental attention over a KV
cache. Word-level timestamps need the cross-attention DTW trick, which is a
second pass and can wait.

## DeepFilterNet3 — voice denoising

- **Package** `DeepFilterRunner` · **Licence** MIT *or* Apache-2.0 (dual, your choice)
- **Weights** `gen/deepfilternet/DeepFilterNet3.zip` (7.7 MB, fetched)
- **Upstream** https://github.com/Rikorose/DeepFilterNet

The smallest model here by two orders of magnitude — roughly 2 MB of actual
weights. Removes room tone, hum and hiss from dialogue in real time.

Works entirely in the complex STFT domain, and `view_as_complex` /
`view_as_real` are already ops the runtime has (they went in for RoPE). So once
Whisper's FFT exists this is close to free.

## Demucs v4 (htdemucs) — stem separation

- **Package** `DemucsRunner` · **Licence** MIT · **Weights** `gen/demucs/htdemucs.th` (81 MB, fetched)
- **Upstream** https://github.com/adefossez/demucs

Splits a mix into vocals / drums / bass / other. In an edit that means pulling
dialogue off a music bed, or replacing the bed and keeping the dialogue.

**Not a duplicate of DeepFilterNet3.** Separation, not denoising: it will not
clean a noisy recording, and DFN3 will not remove a song. Both are cheap and both
want the same FFT.

Hybrid Transformer Demucs runs a waveform branch and a spectrogram branch and
sums them, so the FFT lives *inside* the graph rather than only in a front end.
That makes this the model that decides whether the FFT is a real device kernel or
a host convenience.

## Kokoro-82M — text → speech

- **Package** `KokoroRunner` · **Licence** Apache-2.0 · **Weights** `gen/kokoro` (313 MB, fetched)
- **Upstream** https://github.com/hexgrad/kokoro

82M parameters, 54 fixed voices, no cloning. Chatterbox (MIT, ~0.5B) is the
alternative if voice cloning turns out to matter, but it wants 8 GB+ of VRAM for
it and Kokoro wins on every other axis.

**The awkward one.** StyleTTS2-derived, so LSTMs: a sequential dependency along
time, the shape a GPU is worst at, and the runtime has no answer for it. Also
needs an iSTFT vocoder and `weight_norm` folded at export. Scheduled late
deliberately.

## Image-Adaptive 3D LUT — style / mood grading

- **Package** `NeuralLUTRunner` · **Licence** Apache-2.0
- **Weights** in the upstream checkout (a few hundred KB) — needs `dev/Image-Adaptive-3DLUT`
- **Upstream** https://github.com/HuiZeng/Image-Adaptive-3DLUT

Under 600K parameters. A small CNN predicts blend weights over a few basis 3D
LUTs; the output is a LUT.

**That output shape is the whole argument.** Per-frame diffusion style transfer
flickers, is slow, and hands back an image the user cannot touch. A predicted LUT
is a first-class grading object: it drops into the inspector, the user can push
it around, and it keyframes with the machinery already built. Temporal stability
comes from smoothing the predicted weights across frames, not from the network.

The apply is trilinear interpolation into a 33³ table and belongs in
`GPUFiltering`, not in the graph.

Alternatives if a global grade proves too weak: NLUT (video-specific), SA-LUT
(spatially adaptive 4D), FastLLVE (low-light). Same family, same output shape.

## RIFE 4.x — frame interpolation

- **Package** `RIFERunner` · **Licence** MIT
- **Weights** `gen/rife/train_log/flownet.pkl` (24.6 MB, fetched)
- **Upstream** https://github.com/hzwer/Practical-RIFE

Slow motion, framerate conversion and retime smoothing. Cheap for the runtime:
the warp is `grid_sampler_2d`, already implemented and already exercised by the
optical-flow path in `GPUFiltering`.

**Version 4.26** (2024-09-21), the newest full model — 4.25.lite is dated later
but is the reduced one. The archive carries the architecture next to the weights
(`IFNet_HDv3.py`, `RIFE_HDv3.py`, `refine.py`), so unlike the other models here
the export needs no separate upstream checkout.

Upstream publishes only to Google Drive and Baidu, so the registry fetches this
one through `gdown`: a Drive file over 25 MB serves an HTML virus-scan
interstitial to plain HTTP, and `urllib` writes that web page out as if it were
the weights. `uv run tools/models.py fetch rife` handles it and is idempotent.

Still to do before it can be an artifact: `Pkg` speaks HTTP and nothing else, so
`train_log/` needs re-hosting on the JuliaVision assets release. The README
states the model links carry the same MIT licence as the code, so that is
permitted — it is a one-time 25 MB upload, not a licensing question.

## Depth Anything V2 Small — monocular depth

- **Package** `DepthAnythingRunner` · **Licence** Apache-2.0
- **Weights** `gen/depthanything/depth_anything_v2_vits.pth` (95 MB, fetched)
- **Upstream** https://github.com/DepthAnything/Depth-Anything-V2

Buys fake shallow depth of field, depth-keyed grading, parallax push-ins and sky
masks. 25M parameters.

**Small specifically, and this is the licence trap worth remembering.** The repo
is Apache-2.0 and so is the Small checkpoint, but **Base and Large are
CC-BY-NC-4.0** — checked on the HuggingFace API, not assumed. Large is better and
can be added later as its own non-commercial package.

A ViT with scaled-dot-product attention and nothing else unusual, so the runtime
needs nothing new. Pure editor value, no engine work.

## BasicVSR++ — video upscaling

- **Package** `BasicVSRRunner` · **Licence** Apache-2.0 (mmagic)
- **Weights** `gen/basicvsrpp/basicvsr_pp_reds4.pth` (33 MB) · **Graph**
  `gen/graphs/basicvsrpp-fp32` — already exported
- **Upstream** https://github.com/open-mmlab/mmagic

The furthest along: `tools/export_basicvsrpp.py` already produces the graph, and
`BasicVSRRunner.ready()` is already true. What is missing is the ops it needs and
the workload.

7.3M parameters, but the footprint is activations, not weights — it is recurrent
over a clip, so VRAM scales with sequence length. Budget it against clip length,
not parameter count.

**Flow-guided deformable alignment (DCNv2) is the hardest kernel in this set:**
an irregular per-pixel gather with no clean coopmat mapping.

## ProPainter — object removal

- **Package** `ProPainterRunner` · **Licence** ⚠ **S-Lab 1.0 — non-commercial**
- **Weights** `gen/propainter` (191 MB, fetched: ProPainter + RAFT + flow completion)
- **Upstream** https://github.com/sczhou/ProPainter

Remove a boom mic, a logo, a passer-by. SAM 2 produces the mask, this fills the
hole — it compounds a model that already ships, which is the argument for it over
a standalone feature.

**Non-commercial**, verified from the licence text: S-Lab License 1.0, same as
MatAnyone, from the same group at NTU, commercial use by arrangement with the
authors. Survivable because it is its own package — but the editor must degrade
without it.

## Diffusion image editing — the VRAM arithmetic

Added after asking what a diffusion model would buy the editor: generative fill
behind a SAM 2 mask, outpainting to reframe 16:9 to 9:16 without cropping,
replacing a sign, relighting a subject. That is *editing*, not text-to-image;
txt2img mostly buys title cards.

The whole edit-capable field, measured from the HuggingFace API rather than from
model cards, as bf16 weights:

| model | licence | gated | DiT | text encoder | fits unquantised |
|---|---|---|---|---|---|
| **FLUX.2-klein-4B** | Apache-2.0 | no | **7.8 GB** | 8.0 GB | **yes** |
| OmniGen2 | Apache-2.0 | no | 15.9 GB | in DiT | no |
| FLUX.1-Kontext-dev | other | auto | 23.8 GB | 9.8 GB | no |
| Step1X-Edit-v1p2 | Apache-2.0 | no | 24.9 GB | 16.6 GB | no |
| HiDream-E1-1 | MIT | no | 34.2 GB | 3.3 GB | no |
| Qwen-Image-Edit-2511 | Apache-2.0 | no | 40.9 GB | 16.6 GB | no |

**FLUX.2-klein-4B is the only one that runs at full precision on this card**, and
it is not a lesser feature set: the card states "text-to-image and image-to-image
multi-reference editing in a single unified model", 4 steps, ~13 GB.

**Qwen-Image-Edit-2511 does not fit and the gap is not small.** Its transformer
alone is 40.9 GB, two and a half times the whole budget, and its Qwen2.5-VL text
encoder is another 16.6 GB. The published GGUF ladder:

| build | size | fits alongside encoder + VAE + editor |
|---|---|---|
| BF16 | 40.9 GB | no |
| Q8_0 | 21.8 GB | no |
| Q4_K_M (the usual quality knee) | 13.2 GB | no |
| Q4_0 | 11.9 GB | barely |
| Q3_K_M | 9.9 GB | yes |

So making Qwen the first target means making **int4 dequant in the GEMM epilogue**
the first target, and then judging the model two bits below where it looks its
best. The mechanism is the same epilogue that already folds SAM 2's gelu, so it
is not exotic work — but it is a prerequisite, not a bonus, and it is the
difference between "port a model" and "build a quantisation path first".

The cheap way to settle it is a PyTorch A/B before any porting: klein-4B at bf16
against Qwen at Q4_0 on the same edit. That is what `tools/demos.py` is for.

**Engine cost, shared by all of them:** `group_norm` (missing), a VAE decoder,
and the sampler loop on the host. Notably *not* the KV cache — text encoders are
a single encoder-only forward, which the runtime already does.

## Notes

**Total weights: 2.3 GB.** Wan 2.2's VAE decoder alone was 2.7 GB. Nothing in
this set is a fitting problem; all nine can be resident alongside SAM 2 and
MatAnyone inside the real budget, which is 8–12 GB once the desktop's 3.9 GB and
the editor's frame buffers are accounted for.

**No `Artifacts.toml` yet, for any of them.** A lazy artifact needs the sha256 of
a tarball that has been uploaded to a release, and there is nothing to upload
until an export runs. Until then `DNNKernels.assetpath` falls through to
`gen/graphs/<name>` and the error names the path it looked in. Cutting the
release is what turns a working port into an installable one.

**The monorepo name is now wrong.** Two of these are audio models, and
`JuliaVision` is not where a speech recogniser belongs. Renaming is a separate job.
